# Phase 5: FPF 审查 (First Principles Framework Review)

## 概述

FPF (First Principles Framework) 审查是实施前的质量关卡，使用第一性原理方法验证文档质量。通过 6 阶段审查 (Q0-Q5) 确保需求、设计、任务的完整性和一致性。

**关键指标**: R_eff (有效可靠性) ≥ 0.90 才能进入实施阶段

**R_eff 机械规则**: R_eff = min(D1..D5)，**禁止任何手工上调/下调**（自报凑分上修与无理由下折，两个方向都实际发生过）。

**审查者要求**: FPF 审查者必须 fresh-context（新会话/新 subagent，非作者自评）。
> 依据：004 批次 23 套自报全过，独立复审发现 4 套实际未达门——自报 R_eff 系统性乐观。

## 输入

- `00-discovery.md` - 需求发现文档（矩阵模式下由需求文档替代，默认缺省）
- `01-requirements.md` - 需求规范文档
- `02-design.md` - 技术设计文档
- `03-tasks.md` - 任务清单文档

## 输出

- 默认模式: `.specs/{feature-name}/04-fpf-review.md`
- 矩阵模式: `requirements-specs/{NN-layer}/{PREFIX-NNN-slug}/04-fpf-review.md`

## 审查边界声明（FPF 能力边界）

FPF 验证的是**文档内部一致性 + 已核对锚点**，不承保以下四类风险（一律移交 Phase 6/7 运行时门）：

1. **代码快照时效** — 批量波次实施使前提失效（对策：Phase 6 Step 6.0 前提复核）
2. **跨 spec 组合效应** — 各自全过、组合 build 失败（对策：Phase 7 全量生产 build 集成门）
3. **验证环境保真度** — 本地通过 ≠ 容器/灰度通过（对策：Phase 7 验证环境预检）
4. **外部状态写语义** — 只查了"名字一致"，没查**谁在何时写你读的状态**（对策：Q2 外部状态写语义检查类别，见下文）

每次审查必须显式声明：**证据基线**（runtime 核对日期）+ **未验证面清单**。
> 依据：007 UI-004 NEXT_LOCALE P0——FPF 核过 cookie 名一致（R_eff 0.92），却没人核"中间件会在首个无 cookie 响应上无条件写入该 cookie"，导致目标人群永远看不到提示条。

## FPF 6 阶段详解

### Q0: Init (初始化)

**目标**: 定义审查范围和评估维度

**操作**:
1. 确认审查对象
2. 定义评估维度
3. 设定评分标准
4. 记录**证据基线**（runtime 核对日期：本次审查所核对的代码状态是哪一天的 HEAD/工作区；未提交的工作区状态也算 runtime 真相）

> 依据：审查边界声明要求——无证据基线日期，Phase 6 前提复核就无从判断锚点是否已过期。

**标准维度**:
| 维度 | 代号 | 说明 |
|------|------|------|
| 需求完整性 | D1 | 需求是否完整覆盖功能目标 |
| 设计覆盖率 | D2 | 设计是否覆盖所有需求 |
| 任务追溯性 | D3 | 任务是否追溯到需求 |
| 术语一致性 | D4 | 术语使用是否一致 |
| 可测试性 | D5 | 属性和任务是否可测试 |

**评分标准（带宽固定，旧文案"及格/可接受"作废）**:
| 分数带 | 判定 |
|--------|------|
| ≥ 0.95 | 直接实施 |
| 0.90-0.94 | 小幅修正后实施（不得写作"直接实施"） |
| 0.80-0.89 | 不可实施（修正后重审） |
| < 0.80 | 重新设计 |

**输出格式**: 见 [04-fpf-review 模板](../templates/04-fpf-review.template.md)（权威源，勿在此处复写）。

---

### Q1: Hypothesize (假设)

**目标**: 建立质量假设，预测可能的问题

**操作**:
1. 基于经验预测问题
2. 列出检查重点
3. 设定预期分数

**假设类型**:
| 类型 | 说明 | 示例 |
|------|------|------|
| H1 | 完整性假设 | 所有需求都有对应任务 |
| H2 | 一致性假设 | 术语在所有文档中一致 |
| H3 | 覆盖性假设 | 所有属性都可测试 |

每个假设写明：假设内容、检查方法、预期分数、风险点。

**输出格式**: 见 [04-fpf-review 模板](../templates/04-fpf-review.template.md) Q1 节（权威源，勿在此处复写）。

---

### Q2: Verify (验证)

**目标**: 逐项验证假设，记录发现

**操作**:
1. 按维度逐项检查
2. 记录问题和证据
3. 计算维度分数（分数 = 通过项数 / 总检查项数）

**各维度核心检查项**:

| 维度 | 核心检查项 |
|------|-----------|
| D1 需求完整性 | 功能目标 → 需求映射；技术约束 → 需求映射 |
| D2 设计覆盖率 | 需求 → 属性映射；Prework Analysis 完整性 |
| D3 任务追溯性 | 追溯矩阵完整性；Validates 字段正确性 |
| D4 术语一致性 | 术语表术语使用；跨文档术语一致性 |
| D5 可测试性 | 属性可测试性；验收标准可测试性 |

**输出格式**（逐维度检查项表 + 问题清单 + 维度分数）: 见 [04-fpf-review 模板](../templates/04-fpf-review.template.md) Q2 节（权威源，勿在此处复写）。

**强制检查规则**:

#### 规则 A: 可数断言必须实际执行核数

可数断言（"共 N 处 / N 个文件"）必须实际执行 `grep -c` 核数，不得目测。行号锚点核对不等于数量核对——两者都要做。
> 依据：004 批次——数量断言是 code-truth 漏检重灾区，"全仓仅剩一份"的 FPF 判定实测为事实错误（基线实有 9 处）。

#### 规则 B: 外部状态写语义检查（新增检查类别）

凡设计**读取外部状态**（cookie / header / localStorage / env / DB 行）作为判定依据，审查者必须定位到**写入该状态的代码路径**，核实 spec 对以下三点的假设：写入者身份、写入时机、默认值。仅核"名字/锚点一致"不足以核销本检查。
> 依据：007 UI-004 NEXT_LOCALE P0——名称一致性检查通过（R_eff 0.92），但中间件在任何无 cookie 的首次响应上无条件写入该 cookie，"cookie 存在 = 用户已选择"的核心假设从未被核过。

#### 规则 C: D5 结构性上限如实计分

依赖手测/截图/生产执行的 AC 构成 D5 结构性上限（固有制约，非文档缺陷）——如实计分并记录上限原因，**禁止为凑 R_eff 手工上修**。
> 依据：004 批次独立复审——此类 AC 是"各套无法达 0.95 的固有制约"，而被粉饰的那套恰恰在该维度虚高。

---

### Q3: Validate (交叉验证)

**目标**: 交叉验证文档间的一致性

**操作**:
1. 检查文档间引用
2. 验证数据一致性
3. 确认无矛盾
4. 核对文档断言与 runtime 是否一致（漂移时走 P-CAL，见下）

**交叉验证矩阵格式**: 见 [04-fpf-review 模板](../templates/04-fpf-review.template.md) Q3 节（权威源，勿在此处复写）。

#### P-CAL 校准前提模式（需求文档漂移于 runtime 时）

WHEN Q3 发现源需求文档与 runtime 漂移（未提交的工作区状态也算 runtime 真相），审查 SHALL 以显式前提钉住 runtime 真相，防止测试编码过期 spec：

1. 在 04-fpf-review.md 记录编号校准前提（`P-CAL-1`、`P-CAL-2`…），逐条写明"需求文档口径 → runtime 实际口径 → 裁决依据（runtime>canon）"
2. 按 runtime 真相修补 design/tasks，并把纠偏回馈给源需求文档
3. 发现的上游未实现缺口路由回其归属 spec，而不是本 spec 默默吸收
4. **禁止**按过期 spec 描述编写测试断言（会造成假红/假绿——测试把过期口径冻结成合同）

> 依据：006 QA-002——补发过期语义已改为错峰而需求文档未跟上，审查以 P-CAL-1/P-CAL-2 钉住真实代码后，测试断言才对齐当前实现而非过时描述。

---

### Q4: Audit (审计)

**目标**: 识别风险和改进点

**操作**:
1. 汇总所有问题
2. 评估风险等级
3. 提出改进建议

**风险等级**:
| 等级 | 说明 | 处理方式 |
|------|------|---------|
| Critical | 阻塞实施 | 必须修复 |
| High | 影响质量 | 应该修复 |
| Medium | 可能问题 | 建议修复 |
| Low | 轻微问题 | 可选修复 |

**输出格式**（问题汇总表 + 改进建议）: 见 [04-fpf-review 模板](../templates/04-fpf-review.template.md) Q4 节（权威源，勿在此处复写）。

---

### Q5: Decide (决策)

**目标**: 计算 R_eff，做出决策

**R_eff 计算 (WLNK 原则，机械规则)**:

```
R_eff = min(D1, D2, D3, D4, D5)

WLNK = Weakest Link (最弱环节)
系统可靠性取决于最弱的环节
```

- R_eff 是机械 min，**禁止任何手工上调/下调**——不允许"综合考虑后上修"，也不允许无理由下折头值
- **反通胀**: 全维 1.00 触发复核而非默认接受——先怀疑评分流程漏检，复核证据后方可维持
> 依据：004 批次实锤——自报凑分上修 D5 与无理由下折，两个方向都发生过；23 套自报全过，独立复审 4 套实际未达门。

**决策带宽（固定，禁止改写动作名）**:
- [ ] R_eff ≥ 0.95: 直接实施
- [ ] R_eff 0.90-0.94: 小幅修正后实施（不得写作"直接实施"）
- [ ] R_eff 0.80-0.89: 不可实施（修正后重审）
- [ ] R_eff < 0.80: 重新设计

**计算示例与输出格式**: 见 [04-fpf-review 模板](../templates/04-fpf-review.template.md) Q5 节（权威源，勿在此处复写）。

## 决策标准

### 决策 A: 直接实施 (R_eff ≥ 0.95)

**条件**: 所有维度分数 ≥ 0.95

**行动**:
1. 记录审查结果
2. 获取用户确认
3. 进入 Phase 6 实施

---

### 决策 B: 小幅修正后实施 (R_eff 0.90-0.94)

**条件**: 最低维度分数在 0.90-0.94 之间（动作名固定为「小幅修正后实施」，不得写作"直接实施"）

**行动**:
1. 修复 High 级别问题
2. 更新相关文档
3. 快速复查修正项
4. 获取用户确认
5. 进入 Phase 6 实施

---

### 决策 C: 不可实施（修正后重审）(R_eff 0.80-0.89)

**条件**: 最低维度分数在 0.80-0.89 之间（该带宽判定为**不可实施**；旧文案"及格/可接受"作废）

**行动**:
1. 修复所有 Critical 和 High 级别问题
2. 更新相关文档
3. 重新执行 Q2-Q5
4. 确认 R_eff ≥ 0.90
5. 获取用户确认
6. 进入 Phase 6 实施

---

### 决策 D: 重新设计 (R_eff < 0.80)

**条件**: 最低维度分数 < 0.80

**行动**:
1. 分析根本原因
2. 返回 Phase 1-4 重新设计
3. 完成后重新执行 FPF 审查

## 常见问题

### Q1: 维度分数如何计算？

**方法**:
```
维度分数 = 通过项数 / 总检查项数

示例:
D1 检查项: 10 个
通过项: 9 个
D1 分数 = 9/10 = 0.90
```

注意：检查项中的可数断言必须实际执行 `grep -c` 核数后才能计入通过项。

### Q2: 如何处理主观判断？

**解决方案**:
1. 使用具体的检查清单
2. 记录判断依据
3. 保持一致的标准
4. 主观分歧不得以"手工调整 R_eff"解决——修检查项，不修分数

### Q3: 修正后需要完整重新审查吗？

**解决方案**:
- R_eff 0.90-0.94（小幅修正后实施）: 只需复查修正项
- R_eff 0.80-0.89（不可实施（修正后重审））: 重新执行 Q2-Q5
- R_eff < 0.80（重新设计）: 完整重新审查
