# Phase 7: 验证回归 (Verification & Regression)

## 概述

验证回归阶段是开发流程的最后一步，确保功能正确实现、无回归问题，并以**收口记录**完成闭环。

本阶段的核心是**对抗验证（Adversarial Verification）**：由独立验证者（非实施者）不读实施自报告，逐 AC 重新执行验证命令、独立重推事实，产出 per-spec verdict（`PASS`/`PARTIAL`/`FAIL`）；FAIL/PARTIAL 进入修复→复验循环，闭环后才写收口记录。

**铁律：无收口记录 = 未收口。**

## 输入

- 已完成的代码实现
- `00-discovery.md` 中记录的**项目验证 battery**（权威验证命令清单；矩阵模式下见需求文档/批次文档）
- `02-design.md` - 正确性属性（含 oracle 声明）
- `03-tasks.md` - 验收标准
- 测试代码

## 输出

- 对抗验证 verdict（per-spec：`PASS` / `PARTIAL` / `FAIL` + issues[]）
- 验证报告
- **收口记录**（写回 `03-tasks.md` 尾部——本阶段终步）
- 验收记录归档
- 合并到主分支

## 验证 battery：权威来源

Phase 7 执行的自动化验证命令，以 **Discovery 阶段记录的项目验证 battery** 为唯一权威来源（battery 的来源通常是项目已晋升的规则文件——本工作区见 `.claude/rules/testing.md`）。

本文档中出现的通用命令一律是**显式标注的 fallback 示例**，仅当项目未记录 battery 时临时使用，且用后应回填 Discovery。`<pm>` 代表项目声明的包管理器（以 package.json 的 `packageManager` 字段 / lockfile / Discovery 记录为准）。

## 详细步骤

### Step 7.0: 验证环境预检

验证结论的可信度以验证环境为上限。开始验证前逐项确认：

- [ ] **浏览器/截图证据用生产 build**：dev 模式的按需编译/资产加载可能产生与生产无关的假失败（页面骨架崩坏、chunk 报错）
- [ ] **build 后重启服务**：部分生产服务器启动即快照构建产物、不热更——build 后不重启，验证到的是旧代码
- [ ] **DB 处于迁移头（migration head）**：schema 落后会把新功能误判为回归
- [ ] **worktree 预备**：在 git worktree 中验证前，先补 node_modules（symlink 或安装）并执行内容生成管线（如有），否则会出现成批与本次改动无关的假报错
- [ ] **勿并发跑两个全量测试**：资源争用会制造假超时
- [ ] 记录**验证环境保真度注记**：验证环境与生产形态的差距（如本地生产 build 启动 ≠ 容器 standalone 运行时），最终写入收口记录

**验证清单**:
```markdown

**测试统计**:
- 总测试数: XX / 通过: XX / 失败: 0 / 跳过: 0
- 覆盖率: XX%（阈值以项目规则为准）

**新增测试**: [列出]
```

**检查点**:
- [ ] battery 全绿
- [ ] 覆盖率达标
- [ ] 无新增警告

### Step 7.2: 验证正确性属性

**操作**:
1. 对照 02-design.md 的属性列表
2. 确认每个属性有对应测试/验证动作
3. **按属性声明的 oracle 类型执行**：源码 grep（仓库级不变量）/ HTTP 抓取 / 浏览器 DOM（Playwright）/ DB truth / 执行证据
4. 确认全部通过

oracle 与验证手段不匹配的验证不算数——例：CSR-bailout 的页面内容用 curl 验证会得出错误结论，必须用源码 grep 或真浏览器；仓库级不变量（"字面值全仓归零"）必须全仓 grep，文件清单只是工作项不是验证边界。

**验证表格**:
```markdown
| Property | Oracle | 测试/命令 | 状态 | 备注 |
|----------|--------|-----------|------|------|
| Property 1 | 源码 grep | [命令] | ✅ Pass | |
| Property 2 | 浏览器 DOM | [脚本] | ✅ Pass | |
| Property 3 | DB truth | [查询] | ✅ Pass | |
```

### Step 7.3: 执行回归对比

**目标**: 确保现有功能不受影响，无新增失败、无测试被意外删除。

**禁止**在同一工作区 `git checkout main` 再跑测试做对比——切换会污染当前工作区状态（丢失未提交产物、触发依赖/生成物漂移），且切换本身改变了验证环境，对比结果不可信。

**正确方法（二选一）**:
1. **CI 基线对照**：以主分支最近一次 CI 绿灯运行结果为基线，与当前分支结果对比
2. **独立 worktree 对照**：`git worktree add` 出主分支的独立工作树（按 Step 7.0 完成 worktree 预备），在其中跑基线

```bash
# 独立 worktree 对照示例
git worktree add ../baseline-main main
# （按 Step 7.0 预备该 worktree 的依赖与内容生成）
(cd ../baseline-main && <pm> test > /tmp/main-test-results.txt)
<pm> test > /tmp/feature-test-results.txt
diff /tmp/main-test-results.txt /tmp/feature-test-results.txt
```

**回归对比记录**:
```markdown
| 指标 | 基线（main） | 当前分支 | 差异 |
|------|-------------|---------|------|
| 总测试数 | 150 | 165 | +15 |
| 通过率 | 100% | 100% | 0% |
| 覆盖率 | 85% | 87% | +2% |
```

**检查点**:
- [ ] 无新增失败测试
- [ ] 无测试被意外删除
- [ ] 性能无明显下降

### Step 7.4: 集成门（批量实施必做）

批量/并行实施时，每批至少一次**全量生产 build 集成门**（整棵树，而非 per-spec 隔离验证）：

- 跨 spec 组合效应——各 spec 单独验证全过、组合起来 build 失败（典型如 i18n 命名空间缺口、共享文件键冲突）——**只有全量 build 才撞得出来**（FPF 能力边界第 2 类，FPF 不承保，由本门把守）
- 集成门在多 spec 波次中失败时，用 git stash/bisect 把缺陷**归属到 owning spec** 再修，归属结论写进相关双方的收口记录

**Fallback 示例**:
```bash
<pm> exec tsc --noEmit   # fallback: 全量类型检查
<pm> run build           # fallback: 全量生产 build
```

### Step 7.5: 自动化交付物与门控功能核销

**文件存在 ≠ 功能工作。**

- **自动化交付物（CI workflow / cron / 脚本）必须以执行证据核销**：至少一次真实运行记录（运行日志、执行历史、产物时间戳），禁止用"文件名 + 行数存在"核销。典型事故类别：**workflow 文件存在但从未执行过一次**——期间所有"CI 会拦住回归"的假设全部落空，直到独立审计才发现是死目录
  - **008 实证**: DEP-001 收口取的是真实 **CI-run FAILURE 的 run id**（证明 workflow 真被触发过、且当前真状态），而非"workflow 文件已提交"；CODE-002 的守门核销是**亲跑 14 行变异矩阵**取红/绿输出，而非"守护测试文件存在"。文件在磁盘上 ≠ 它跑过、≠ 它会拦。
- **flag 门控功能必须 flag-on 验证**：smoke 走旁路（flag-off 路径）通过 ≠ 功能可用；至少一次开闸状态下的真实链路验证
- **mock 遮蔽警示**：测试把接线点 mock 掉时，全绿证明不了链路存在。对"接线"类 AC（A 调用 B、脚本被门消费、事件被写入），验证必须穿透到真实接线点（真实调用 / 真实配置 / 真实 DB）

---

### Step 7.6: 变异守门 (Mutation Guard)

新增守门测试/门禁（"X 永不出现"、"基线不得回退"类），必须做**变异守门**：

1. 临时破坏被守护面（注入违规值 / 删除被守护结构）
2. 观察门转红
3. 还原，观察门转绿
4. 归档红/绿两次输出

**从未见过红的守门不算覆盖。** 配套规则（守门测试质量）:

- 期望值必须派生自 SSOT/运行时规则源，**禁止 pin 观察值**（实锤：pin 观察值把 P0 定价 bug 冻结成合同——测试通过恰恰因为它断言了错误的现状）
- 行为反转类改动必须翻转旧 pinned 守门（旧断言编码旧行为，新行为落地后它们会成批变红或——更糟——继续绿着守护错误）
- mock/fixture 是合同面，行为变更时同步审

### Step 7.8: 对抗验证 (Adversarial Verification) — 核心步骤

自动化全绿不是终点。实施者验证自己的工作有系统性盲区，必须由**独立验证者**做一轮不信任式复核。

**验证者要求**:
- 新 subagent / 新会话，**非实施者**
- **不读实施自报告**（自报告会锚定注意力，复刻实施者的盲区）

**操作**（逐 spec）:
1. 逐 AC 重新执行验证命令
2. 独立重推事实：grep / build / curl / DB 查询——亲手取证，不采信转述
3. 产出 per-spec verdict:

| Verdict | 含义 | 后续 |
|---------|------|------|
| `PASS` | 全部 AC 独立复核通过 | 可进入收口 |
| `PARTIAL` | 部分 AC 未达或证据不足 | 修复→复验循环 |
| `FAIL` | 关键 AC 不成立 | 修复→复验循环 |

4. `PARTIAL`/`FAIL` 必须附 **issues[]**，每条含：
   - `file`: 问题所在文件
   - `description`: 问题描述（可独立理解）
   - `suggestedFix`: 建议修复方向（可供修复 agent 直接行动）
5. **修复→复验循环**: 修复后由验证者重新复核对应 AC，直至 PASS；**闭环后才写收口记录**

**3 镜头并行编排（008 配方）**: Workflow 编排下，同一 spec 派 **3 个独立验证 agent 并行**，各从不同证据面重推（源码 grep / build-or-runtime / DB-or-CI 执行证据），互不读对方与实施者的自报告。并行提速 + 多视角互补，覆盖单一验证者易漏的证据面。

**证据 1**: 某批次四波对抗验证抓出 4 个 R_eff≥0.90 且测试全绿仍漏掉的真实缺陷（含 1 个 P0：目标人群永远看不到提示条）。

**证据 2（008 假绿实锤，运行中不干预 × 验证者≠作者）**: 主线程误判某 Workflow 的 TaskList 空 = 实施 agent 已死，抢先提交"恢复" commit，与仍在跑的工作流竞速，**捕获了工作流的变异注入中间态 → 提交假绿**。该假绿被工作流**自身的独立验证 agent** 抓获并 supersede 修复（`5ce67e71`）。双重教训: ① `TaskList 空 ≠ 工作流死`，运行中的工作流绝不干预（凭完成通知判死活）；② 验证者与作者是不同实例——正因如此，作者（主线程）的假绿被验证者独立拦下。

**特殊裁决**: 对抗验证发现的"FAIL"若经查是 spec 前提已被早波取代（非实现遗漏），按 Phase 6 Step 6.0 分类 (b) 处理——收口记录判 `spec-premise-stale`，引用取代方设计决策，不算实施失败。

### Step 7.10: 部署收口（仅当部署在本次范围内）

**发布 ≠ 完成。** 部署类任务按**证据层级**收口，高层证据可推翻低层证据，反向禁止：

```
DB truth > 容器池状态 + 公网健康端点 > smoke 结果 > wrapper 退出码 / marker 文件
```

- 不得用部署脚本的成功文案推翻 DB 事实；不得用单个 curl 200 推翻真实客户端红字
- **三面一致性**逐面核销，缺一不可：
  1. **Git synced**: 本地 HEAD 与远端主分支一致
  2. **部署 payload synced**: 远端部署目录关键文件与发布 commit 一致（hash/manifest 比对）
  3. **Runtime deployed**: 运行容器为目标镜像且 healthy、生产 smoke 通过
- 未走完外部门的任务用双态标记：`✅ 本地完成` / `外部门待验`，禁止把"已合并"写成"已上线"
- 具体部署验收命令与环境基线属于工作区规则——本工作区见 `.claude/rules/gce-deployment.md`

### Step 7.13: 终步——写收口记录回 03-tasks.md

**这是 Phase 7 的收尾动作，也是 spec 闭环的唯一凭证。**

**铁律：无收口记录 = 未收口；批量实施时每个 spec 都要写（含早波——早波不能因为"当时看着顺利"就免写）。**

在 `03-tasks.md` 尾部写入「收口记录」，字段：

| 字段 | 内容 |
|------|------|
| 日期 | YYYY-MM-DD |
| 状态判定 | 五态词汇（固定拼写）：`PASS` / `PARTIAL→已修复→PASS` / `FAIL→已修复` / `spec-premise-stale`（前提过期不实施，附裁决依据+引用取代方的设计决策）/ `deferred-non-blocking`（延期不阻塞，列明登记去处） |
| 实施摘要 | 按任务 |
| 偏差清单 | 含「等价实施偏差」：运行时更优时允许偏离 spec 字面，一行留痕即免未来复推；含 design-errata 勘误（原断言/代码证据/裁决） |
| 发现的范围外问题 | 及归属 spec/新登记项 |
| 验证证据 | 命令 + 关键输出（含对抗验证 verdict 与 issues 闭环记录） |
| 验证环境保真度注记 | 验证环境 vs 生产形态差距（如本地生产 build 启动 ≠ 容器 standalone 运行时） |

**证据**: 某批次 10/21 有收口记录的 specs 全程可追溯，11 个没写的（含两个 P0）实施真相失传。

#### tripwire 冻结收口（无法当期验证的开放项）

当期无法验证或处于休眠（无真实流量触达）的开放项，**不得留成模糊时间欠账**（"以后再看"），用 tripwire 冻结收口：

- 写明**数据触发条件**：什么可观测信号出现时重启该项
- 落一个**测量探针**：让触发条件真的可被观测到（否则触发条件永远不会响）
- 收口记录状态判定用 `deferred-non-blocking`，列明登记去处（决策台账 / INDEX 开放项）

## 验证失败三分诊

任何验证失败先分诊，再行动——三类失败的正确处置完全不同，混着修会把设施问题修成代码回退：

| 分诊 | 特征 | 处置 |
|------|------|------|
| **真回归** | 代码行为确实变坏 | 修复代码，补回归测试 |
| **过期断言** | 行为按设计变了，测试/断言还编码着旧行为 | 更新断言至新 SSOT；行为反转类改动检查是否有成批旧 pinned 守门需要翻转（见 Step 7.6） |
| **验证设施问题** | 环境/工具/fixture 造成的假失败（依赖缺失、并发争用、dev 模式假象、smoke 目标漂移） | 修验证设施，不动业务代码；回 Step 7.0 预检 |

**拓扑变更必须含 smoke 更新任务**：凡改动路由/入口/部署拓扑（页面合并、URL 迁移、服务重排），任务清单必须包含"更新对应 smoke/监控断言"的任务——否则旧 smoke 会变成永久假红，或（更糟）继续假绿地守护已不存在的拓扑。

## 常见问题

### Q1: 测试失败怎么办？

按「验证失败三分诊」归类后处置：
1. 真回归 → 修代码 + 补回归测试
2. 过期断言 → 更新断言至新 SSOT（检查成批 pinned 守门）
3. 验证设施问题 → 修设施，回 Step 7.0

### Q2: 发现回归问题怎么办？

1. 记录回归问题
2. 分析影响范围；批量波次中先用 stash/bisect 归属到 owning spec
3. 修复回归
4. 添加回归测试（按守门测试质量规则：期望值派生自 SSOT，做变异守门）
5. 重新验证，归属结论写进相关收口记录

### Q3: 对抗验证结论与实施者结论冲突怎么办？

以独立重推的事实为准（亲手取证 > 转述；runtime > canon）。若冲突源于 spec 前提已被早波取代，判 `spec-premise-stale`（引用取代方设计决策），不算实施失败。

### Q4: 用户验收反馈不通过怎么办？

1. 记录反馈进验收记录
2. 小问题：直接修复，重跑对应 AC 的对抗验证复核
3. 大问题：返回实施阶段（Phase 6），修复后重新走 Step 7.8 起的闭环
4. 收口记录相应更新状态判定（如 `FAIL→已修复`）
