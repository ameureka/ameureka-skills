# Phase 1: 需求发现 (Discovery)

## 概述

需求发现是整个开发流程的起点，目标是深入理解用户意图、收集背景信息、识别技术约束，并建立统一的术语表。

## 输入

- 用户的功能描述或需求陈述
- 现有代码库访问权限
- 项目文档（如有）

## 输出

按运行模式二选一（模式定义见 [SKILL.md](../SKILL.md)）：

- **默认模式**：`.specs/{feature-name}/00-discovery.md`
- **矩阵模式**（从需求矩阵 requirements/ 批量生成 specs）：输出目录为 `requirements-specs/{NN-layer}/{PREFIX-NNN-slug}/`，且 **00-discovery.md 默认跳过**——上游需求文档（含 runtime 复核记录、约束、术语）即 discovery 产物。仅当需求文档缺少技术约束或术语表时，补一份精简 **discovery-lite**（只含缺失小节，不重复默认模式全量流程）。项目验证 battery（见 Step 1.5）在矩阵模式下登记到批次文档或 INDEX，供全批共享。

## 详细步骤

### Step 1.1: 理解用户意图

**目标**: 明确用户想要实现什么

**操作**:
1. 仔细阅读用户的需求描述
2. 识别核心目标和期望结果
3. 记录任何隐含的假设

**提问清单**:
- 这个功能要解决什么问题？
- 目标用户是谁？
- 成功的标准是什么？
- 有没有类似的参考实现？

**输出格式**:
```markdown
## 功能目标

### 核心目标
[一句话描述功能的核心目标]

### 期望结果
- [结果1]
- [结果2]

### 成功标准
- [标准1]
- [标准2]
```

---

### Step 1.2: 分析现有代码库

**目标**: 了解相关的现有实现和模式

**操作**:
1. 搜索相关的代码文件
2. 分析现有的架构模式
3. 识别可复用的组件
4. 记录代码约定

**搜索策略**:
```bash
# 搜索相关文件
grep -r "关键词" --include="*.ts" --include="*.tsx"

# 查找类似功能
find . -name "*.ts" | xargs grep -l "相关模式"

# 分析目录结构
tree -L 3 src/
```

**输出格式**:
```markdown
## 现有实现分析

### 相关文件
| 文件 | 用途 | 关联度 |
|------|------|--------|
| path/to/file.ts | 描述 | 高/中/低 |

### 现有模式
- [模式1]: [描述]
- [模式2]: [描述]

### 可复用组件
- [组件1]: [如何复用]
```

**⚠️ 警示：旧文档/审计断言不轻信（runtime>canon）**

Discovery 引用的任何来自旧审计、旧设计文档、记忆文件的代码事实断言，必须先做 runtime 抽查（grep/实测）再采信，并在文档中标注验证方式与核对日期。历史上双向翻车都发生过：把「设计过但从未实现」当「已实现有 bug」立项修复，也把文档写的「未接线」当真（实际早已接线）。对关键断言做对抗 confirm/refute（双向证伪）。批量矩阵场景的完整提取纪律见 requirements-matrix-generator 技能的 runtime 复核步骤。

> 防止的失败类别：据过期文档断言立项——修复不存在的 bug，或重复实现已有能力。

---

### Step 1.3: 识别技术约束

**目标**: 明确技术限制和依赖

**操作**:
1. 检查项目依赖
2. 识别框架限制
3. 了解性能要求
4. 记录兼容性需求

**检查清单**:
- [ ] 框架版本限制
- [ ] 浏览器/环境兼容性
- [ ] 性能要求
- [ ] 安全要求
- [ ] 第三方依赖限制

**输出格式**:
```markdown
## 技术约束

### 框架约束
- [框架]: [版本] - [限制说明]

### 依赖约束
- [依赖]: [版本] - [限制说明]

### 性能约束
- [约束1]
- [约束2]

### 兼容性要求
- [要求1]
- [要求2]
```

---

### Step 1.4: 建立术语表

**目标**: 统一术语定义，避免歧义

**操作**:
1. 收集领域术语
2. 定义每个术语的含义
3. 确定中英文对照（如适用）
4. 与用户确认术语

**术语表格式**:
```markdown
## 术语表 (Glossary)

| 英文 | 中文 | 定义 | 使用上下文 |
|------|------|------|------------|
| Term | 术语 | 定义说明 | 在哪里使用 |
```

**术语选择原则**:
1. 优先使用项目中已有的术语
2. 技术术语保持英文（如 API, OAuth）
3. 业务术语使用中文
4. 避免同义词混用

---

### Step 1.5: 记录项目权威验证 battery

**目标**: 把本项目真实使用的验证命令集（typecheck / 测试 / build / 领域专用门）固化为 Discovery 的**命名产物**，Phase 7 只执行这份 battery

**操作**:
1. 查找项目已晋升的验证规则（项目规则文件——本工作区见 `.claude/rules/testing.md` 等、CI workflow、package.json scripts、贡献指南）
2. 逐条登记：命令 + 来源规则文件 + 触发条件（改哪类文件必须跑哪个门）
3. 无已晋升规则时，从 package.json scripts 推导，并显式标注「推导所得，未经项目规则确认」
4. 包管理器按项目声明（pnpm/npm/yarn 等），不要默认 npm

**产物格式**:
```markdown
## 项目验证 battery

| 命令 | 来源 | 触发条件 |
|------|------|---------|
| [typecheck 命令] | [规则文件/CI] | 所有代码改动 |
| [全量单测命令] | [规则文件/CI] | 所有代码改动 |
| [领域专用门] | [规则文件] | 改动 X 类文件时 |
```

**规则**:
- Phase 7 与每个 spec 的收口记录只承认这份 battery，skill 文档中的 generic 示例命令仅作显式标注的 fallback
- 矩阵模式/批量模式下，本产物登记在批次文档或 INDEX，供全批共享

> 防止的失败类别：Phase 7 按 skill 里的 generic 命令验证、漏掉项目权威门——历史批次的真实收口从未使用过 skill 示例命令，全部依赖项目专属 battery（typecheck + 全量测试 + 串行集成 + 领域校验器）。

## 验证检查清单

### 完整性检查

- [ ] **功能目标明确**
  - 核心目标一句话可描述
  - 成功标准可衡量

- [ ] **代码分析完成**
  - 相关文件已识别
  - 现有模式已记录

- [ ] **技术约束已识别**
  - 框架限制已记录
  - 依赖限制已记录

- [ ] **术语表完整**
  - 所有领域术语已定义
  - 中英文对照清晰

- [ ] **项目验证 battery 已记录**
  - 命令 + 来源规则文件 + 触发条件齐全
  - 无已晋升规则时已标注「推导所得」

### 质量检查

- [ ] **无歧义**
  - 术语定义清晰
  - 约束描述具体

- [ ] **可追溯**
  - 每个发现有来源
  - 代码引用有路径

- [ ] **runtime>canon**
  - 引用旧文档/审计的代码事实断言已 runtime 抽查
  - 已标注验证方式与核对日期

- [ ] **用户可理解**
  - 非技术人员可读懂目标
  - 技术细节有解释

## 常见问题

### Q1: 用户需求描述模糊怎么办？

**解决方案**:
1. 列出具体问题清单
2. 提供选项让用户选择
3. 使用示例说明不同理解
4. 记录假设，后续确认

### Q2: 代码库太大，如何快速定位？

**解决方案**:
1. 从入口文件开始
2. 使用 IDE 的引用查找
3. 搜索关键词和模式
4. 查看测试文件了解用法

### Q3: 术语在项目中使用不一致？

**解决方案**:
1. 记录所有变体
2. 选择最常用的作为标准
3. 在术语表中注明别名
4. 建议后续统一
