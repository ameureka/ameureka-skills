# Phase 6: 迭代实施 (Implementation)

## 概述

迭代实施阶段按照任务清单执行开发工作，保持追溯性，确保每个任务都正确完成并通过验收标准。

本阶段有一个置于一切实施动作之前的强制门——**Step 6.0 前提复核（Premise Re-validation）**：spec 是对着编写时刻的代码快照写的，实施时代码可能已经变了；不复核就动手，等于对着过期地图开车。

**前提条件**: FPF 审查通过（R_eff ≥ 0.90，按 R_eff 机械规则判定）且用户已批准进入实施（批量授权模式下由批次级一次性授权记录替代，见「批量/并行实施」）

## 输入

- `00-discovery.md` - 需求发现文档（矩阵模式下由需求文档替代）
- `01-requirements.md` - 需求规范文档
- `02-design.md` - 技术设计文档
- `03-tasks.md` - 任务清单文档
- `04-fpf-review.md` - FPF 审查文档

## 输出

- 实现的代码
- 测试代码
- 更新的 `03-tasks.md`（任务状态 + 偏差留痕）

> 注意：任务状态勾选只是中间态。spec 级闭环以 `03-tasks.md` 尾部的**收口记录**为准（Phase 7 对抗验证闭环后写入）；**无收口记录 = 未收口**。

## 实施原则

### 原则 1: 按优先级执行

**规则**: 按照 03-tasks.md 中定义的顺序执行

**优先级顺序**:
1. 基础设施任务 (配置、类型定义)
2. 核心功能任务 (主要实现)
3. 集成任务 (组件连接)
4. 测试任务 (验证代码)
5. 文档任务 (更新文档)

---

### 原则 2: 单任务聚焦

**规则**: 一次只处理一个任务

**工作流**:
```
选择任务 → 实施 → 验证 → 标记完成 → 下一个任务
```

**禁止**:
- ❌ 同时处理多个任务（并行 agent 的分工规则见「批量/并行实施」——单个 agent 内部仍然单任务聚焦）
- ❌ 跳过任务（**阻塞任务除外**，按「问题处理流程」标记 `[!]` 后跳到下一可执行任务）
- ❌ 修改任务范围（等价实施偏差与 design-errata 裁决除外，两者均须留痕，见「批量/并行实施」）

---

### 原则 3: 验收驱动

**规则**: 每个任务必须满足所有验收标准

**验收流程**:
1. 阅读任务的 Acceptance Criteria
2. 实施代码
3. 逐项验证 AC
4. 全部通过后标记完成

---

### 原则 4: 保持追溯

**规则**: 代码变更必须追溯到任务

**追溯方式**:
- Git commit message 引用任务编号
- 代码注释引用需求编号 (如需要)
- 测试名称反映属性编号

---

### 原则 5: runtime > canon

**规则**: spec 文档是对历史快照的描述，代码是当前现实。凡文档与代码冲突，先复核（Step 6.0），再裁决（(a) 就地更新 / (b) `spec-premise-stale` / design-errata 勘误），**禁止机械照搬文档**。

---

## 详细步骤

### Step 6.0: 前提复核 (Premise Re-validation)

**这是实施前的强制门，置于一切实施动作之前。**

批量实施中，实施任何 spec 前：对 01/02/03 中每个 file:line 锚点、key 名、数量断言 grep/Read 重验 against 当前 HEAD；优先核 INDEX 交叉引用热点中被早波触碰的文件。单 spec 实施同理——spec 编写与实施之间的任何提交都可能造成漂移。

**漂移分类**:

| 分类 | 判定 | 处理 |
|------|------|------|
| (a) 琐碎锚点漂移 | 目标仍存在，仅行号/位置/命名微移 | 就地更新 spec 锚点，继续实施 |
| (b) 结构性取代 | 目标文件/key/结构已被更早的设计决策删除或重构 | **禁止机械实施**；收口记录判 `spec-premise-stale`，附裁决依据并引用取代方的设计决策 |

**为什么 (b) 禁止机械实施**: 机械重建已被删除的结构，会与取代方 spec 的显式设计决策直接冲突——这不是"实现遗漏"，而是"spec 前提已过期"，两者的收口结论完全不同。

**证据**: 某批次 21 套 specs 全部对着同一快照写，Wave1 落地后两套晚波 spec 的目标文件/key 已被删除，机械实施会与 Wave1 的设计决策直接冲突。FPF 审查无法捕获此类漂移——它核对的是同一个 pre-wave 快照（见 FPF 能力边界第 1 类：代码快照时效不在 FPF 承保范围内，移交本步骤把守）。

**检查点**:
- [ ] 01/02/03 全部 file:line 锚点、key 名、数量断言已对当前 HEAD grep/Read 重验
- [ ] INDEX 交叉引用热点中被早波触碰的文件已优先核对
- [ ] 漂移已按分类处理：(a) 就地更新 / (b) 判 `spec-premise-stale` 并引用取代方设计决策

**操作**:


**检查点**:
- [ ] 分支已创建
- [ ] 依赖已安装
- [ ] 验证 battery 可运行

**操作**:
1. 打开 `03-tasks.md`
2. 找到第一个未完成的任务
3. 确认依赖任务已完成

**任务状态**:
| 状态 | 标记 | 说明 |

### Step 6.3: 实施任务

**操作**:
1. 阅读任务描述和验收标准
2. 打开要修改的文件
3. 实施代码变更
4. 编写/更新测试

**实施检查清单**:
- [ ] 理解任务目标
- [ ] 理解验收标准
- [ ] 代码符合项目规范
- [ ] 无引入新的 lint 错误
- [ ] 相关测试已编写/更新

**代码规范**:
```typescript
// ✅ 好的代码
export const AVAILABLE_LANGUAGES = [
  { value: 'en' as const, label: 'English', nativeLabel: 'English' },
  { value: 'fr' as const, label: 'French', nativeLabel: 'Français' },
  { value: 'zh' as const, label: 'Chinese', nativeLabel: '简体中文' }  // Task 1.1
] as const;

// ❌ 避免的代码
export const AVAILABLE_LANGUAGES = [
  { value: 'en', label: 'English', nativeLabel: 'English' },
  { value: 'fr', label: 'French', nativeLabel: 'Français' },
  { value: 'zh', label: 'Chinese', nativeLabel: '简体中文' }  // 缺少 as const
];
```

**操作**:
1. 逐项检查验收标准

### Step 6.5: 提交代码

**操作**:
1. 暂存变更
2. **核对 staged 清单 vs 触碰文件清单**
3. 编写 commit message
4. 提交代码

**提交纪律（staged 清单核对，强制）**:

提交前必须核对 `git diff --cached --stat` 输出与本任务实际触碰的文件清单**逐文件一致**——不是看总数，是逐项比对。

```bash
git diff --cached --stat
# 逐项比对任务执行记录中的「文件」清单，缺一不可提交
```

**证据**: 实锤事故——一次提交只暂存了测试文件，8 个 src 改动从未入库；测试全绿的提交实际上不包含被测代码，下游一切「已实施」结论全部失真。

**Commit Message 格式**:
```
<type>(<scope>): <description>

[Task X.Y] <详细说明>

Validates: Req X.Y, Property Z
```

**Type 类型**:
| Type | 说明 |
|------|------|
| feat | 新功能 |
| fix | 修复 |
| docs | 文档 |
| style | 格式 |
| refactor | 重构 |
| test | 测试 |
| chore | 杂项 |

**示例**:
```bash
git add src/shared/constants/i18n.ts
git commit -m "feat(i18n): add Chinese language support

[Task 1.1] Add 'zh' to SupportedLanguage type and AVAILABLE_LANGUAGES array

Validates: Req 1.1, Req 1.2, Property 1, Property 2"
```

### Step 6.6: 更新任务状态

**操作**:
1. 打开 `03-tasks.md`
2. 将任务标记为完成
3. 记录完成时间

**双态任务状态**: 依赖外部门（部署、灰度、真实流量、外部系统）核销的任务，本地做完只能标 `✅ 本地完成`，外部证据到手前保持 `外部门待验`——**发布 ≠ 完成**，禁止把"已合并"直接写成"已上线/已生效"。

**与收口记录的衔接**: 任务级勾选是中间态；spec 级闭环以 `03-tasks.md` 尾部的**收口记录**为准，由 Phase 7 在对抗验证闭环后写入（字段与五态状态判定见 Phase 7 终步）。实施过程中产生的偏差、勘误、范围外发现，要随手记下，最终汇入收口记录对应字段。

**更新示例**:
```markdown
### Task 1.1: 添加中文语言配置 [x]

**Status**: ✅ Completed (YYYY-MM-DD)

**Acceptance Criteria**:
- [x] SupportedLanguage 类型包含 'zh'
- [x] AVAILABLE_LANGUAGES 包含中文条目
- [x] TypeScript 编译通过

**Commit**: abc1234
```

## 批量/并行实施

**适用条件**: 用户给出明确常设授权（批量授权模式，见 SKILL.md「批量模式」）。默认交互模式下仍然逐 spec 确认，本节规则不改变单 spec 流程的其余步骤。

### 分组与落地

- **文件不相交分组**: 并行实施 agent 按"触碰文件集合互不相交"分组，分组依据 INDEX 的共享文件热点表（文件 → 触碰它的需求 ID 列表）；文件集合有交集的 specs 串行或走合并者模式
- **主工作树落地**: 并行 agent 的改动落在主工作树（worktree 隔离会搁浅改动——agent 在隔离 worktree 里完成的修改不会自动汇入落地分支，事后找回成本极高）

### 共享文件：合并者模式 (Consolidator)

热点文件（多个 spec 同批触碰，典型如 i18n messages、路由/导航清单、package.json）**禁止多 agent 直接并发编辑**：

1. 实施 agents 只**申报结构化变更**（set/delete + 值），不直接写热点文件
2. 单一 consolidator 统一应用全部变更并校验（键冲突、格式、构建）
3. 同名脚本/资源命名冲突必须有**归属裁决**：为每个共享产物指定唯一 owner spec，其余 spec 为 consumer-only（实锤：两个 spec 抢同一 package.json script 名，各自 FPF 均通过，结果一方的核心断言库建成且 PASS 但从未接线，部署门目标落空）

### 结构化偏差申报 (Deviations)

每个实施 agent 交付时必须**结构化申报 deviations**：与 spec 字面不同之处 + 理由，逐条列出；没有偏差也要显式申报空列表，**禁止默默偏离**。偏差最终汇入收口记录的「偏差清单」字段。

### design-errata 出口（设计文档事实性错误）

凡 02-design 指定的用户可见内容/数字/产品事实断言，落笔前先对 runtime 重验（runtime > canon）。若核实**设计文档本身含事实性错误**：

1. **不盲从实施错误**——机械照搬会把新的事实性错误发布出去
2. 以 code-as-truth 裁决：就地更正设计文档（勘误），按代码事实实施
3. 收口记录留痕：原断言 / 代码证据 / 裁决结果，三要素齐全

**证据**: 某 spec 的 design 要求把 A 产品线的数字写进 B 产品线的 FAQ 答案；实施 agent 对代码核实两者是完全不同的产品线，就地勘误而非机械照搬，避免把项目本来要修的那类事实性错误重新引入。FPF（R_eff 0.92）未能捕获——它审的是结构一致性，不重推设计中的产品事实断言。

**上游同理，勘误始于生成期（008 实证）**: 每层不信上层字面，独立 runtime 复核。008 spec **生成期**的独立复核就抓获 10+ 处需求/审计字面勘误——例如 CODE-001「统一到 /api/v1」按字面会打断 Claude Code 的既有路由，改判 **domain-only**（只统一文档域名，不动运行时路由）；UI-004 的 ACC-18 引用的是一处对代码已过期的注释。教训: 需求文档的字面 ≠ runtime 真相，生成 spec 时就要独立 grep 复核，把勘误拦在实施之前。

### 等价实施偏差台账

当运行时现状比 spec 字面更优（更简洁、复用现有模式、语义等价）时，允许偏离 spec 字面实施，条件是在收口记录「偏差清单」中**一行留痕**（偏了什么、为何等价/更优）。一行留痕即免未来复推——不留痕的等价偏差，后人对不上 spec 与代码，只能重新考古。

### 波次回归门与波间复核

- 每波结束跑**全量回归门**（类型检查 + 全量测试 + 生产 build）绿后才 commit——跨 spec 组合效应只有全量 build 才撞得出来（见 Phase 7「集成门」）
- 每波开始前对本波 specs 重跑 **Step 6.0 前提复核**——早波已经改变了代码现实

### Workflow 编排载体（008 推荐配方）

批量实施优先用 **Workflow 编排**而非逐个 Agent 手工调度: 一波一 Workflow，波内三段固定为「串行实施（依赖序）→ 每件 3 镜头独立对抗验证 parallel → 修复」。收益: 断点续跑、验证/实施实例隔离由编排层保证、每波回归门+commit 由编排层强制。008 = 4 波 4 Workflow，12/12 全终态。详见 SKILL.md「批量模式 > Workflow 编排」。

### 中断恢复：撞限先盘磁盘（disk-recovery，008 黄金纪律）

批量长跑必遇中断（auth 瞬时掉线 / 会话或周配额硬上限 / 5h 限额）。agent 死于 commit 前**常已写完文件只丢返回值**——恢复的第一动作是**盘磁盘**，不是重做:

1. `git status` / `git diff` / 读目标文件，确认已落盘的成果
2. 已落盘的直接接续（补 commit / 补收口记录），仅真缺失的部分重做
3. 我方缩小被扫窗口: **edit→即时 commit**（并发场景尤要，减少未提交编辑被破坏性 git 丢弃的暴露）

**运行中的工作流绝不干预**: `TaskList 空 ≠ 工作流死`。008 主线程误判抢先提交，与运行中工作流竞速捕获变异注入中间态 → 假绿（被工作流自身验证 agent supersede 修复 `5ce67e71`）。凭完成通知判死活，禁凭进度快照推断。

**008 实证零重做救回**: UI-003 Task0 基线、CODE-002 守护测试、UI-008 llms.txt + 48 处日期——全从磁盘捞回。

## 常见问题处理

### 问题 1: 任务被阻塞

**症状**: 任务依赖的功能不可用

**处理**:
1. 标记任务为 `[!]` 阻塞
2. 记录阻塞原因
3. 跳到下一个可执行任务（这是原则 2「禁止跳过任务」的唯一例外）
4. 阻塞解除后返回处理

```markdown
### Task 2.3: [任务名称] [!]

**Status**: ⚠️ Blocked

**Blocked by**: Task 2.1 未完成
**Blocked since**: YYYY-MM-DD
```

---

### 问题 2: 发现设计问题

**症状**: 实施时发现设计不合理

**处理**（先分型）:
- **结构性设计缺陷**（方案不合理、遗漏组件）: 按下面流程处理——小问题直接修正并更新文档；大问题暂停实施，返回设计阶段
- **事实性错误**（设计中的数字/产品事实与 runtime 不符）: 按「design-errata 出口」处理（就地勘误 + code-as-truth 裁决 + 收口记录留痕），单 spec 模式同样适用
- **前提已被取代**（目标结构已被更早落地的设计决策删除）: 按 Step 6.0 分类 (b) 处理，收口记录判 `spec-premise-stale`

```markdown

**Issue**: [问题描述]
```

### 问题 3: 测试失败

**症状**: 验收测试不通过

**处理**:
1. 按 Phase 7「验证失败三分诊」归类：{真回归 | 过期断言 | 验证设施问题}
2. 按分诊结果修复代码 / 更新断言 / 修验证设施
3. 重新验证
4. 确认通过后继续

```markdown
## Test Failure

**Test**: test_xxx
**Error**: [错误信息]

**分诊**: 真回归 / 过期断言 / 验证设施问题
**Root Cause**: [原因分析]

**Verification**: ✅ 重新运行通过
```

### 问题 4: 范围蔓延

**症状**: 实施时想添加额外功能

**处理**:
1. 记录想法
2. 评估是否在当前范围内

4. 保持当前任务聚焦

## 时间估算

实施时间取决于任务数量和复杂度，参考 03-tasks.md 中的工作量估算。

**一般规律**:
| 任务规模 | 工作量 | 预计时间 |
|---------|--------|---------|
| S (Small) | 1-2 小时 | 半天 |
| M (Medium) | 2-4 小时 | 1 天 |
| L (Large) | 4-8 小时 | 1-2 天 |

**总时间** = Σ(各任务工作量) × 1.2 (缓冲系数)；批量实施另计前提复核与波次回归门时间。
