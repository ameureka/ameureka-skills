# Loop 提示词生成器 (Loop Prompt Generator)

将「我想让 Claude Code 一直跑下去把 X 做完」翻译成一份**可直接粘贴、可中断恢复、有确定性停止条件**的 loop 提示词。

> **语言约定**：正文一律中文；loop 原语 / 状态词 / 命令关键字保留英文（/goal、/loop、PASS、R_eff 等）。

## Quick Reference

**一句话说明**: 输入任务目标 + 动态上下文（队列在哪、质量门是什么、红线有哪些），输出一份 paste-ready 的 loop 提示词 + 操作手册。

**核心流程**:
```
任务画像 → 原语选型 → 停止条件/质量门设计 → 九块组装 → 输出提示词+操作手册
  (1)        (2)            (3)              (4)         (5)
```

**官方定义**（loop.pdf，ClaudeDevs）: loop = agent 重复工作循环直到停止条件命中。按触发方式 / 停止方式 / 所用原语 / 适用任务分四类。

**快速检查**:
- [ ] 停止条件是**确定性 + 磁盘可验证**的（文件存在/状态表值/测试绿），不是"感觉做完了"
- [ ] 有显式轮次/次数上限（"stop after N tries"）
- [ ] **/goal 文本 ≤ 4000 字符**（`wc -m` 实测；超限走契约文件模式：九块落盘，/goal 只装指针+停止条件）
- [ ] 队列真相源在磁盘（状态表/文件清单），不在对话记忆
- [ ] 中断恢复段写明"先盘磁盘再动手"
- [ ] 不可逆/对外动作（部署/发布/删数据）显式排除在自主范围外

## Loop 类型速查表（源自官方 loop.pdf）

| 类型 | 触发 | 停止 | 你交出的是 | 适用 | 原语 |
|------|------|------|-----------|------|------|
| Turn-based | 用户每轮提示 | Claude 判断完成/需上下文 | 检查权（the check） | 探索/决策中的短任务 | 普通提示 + 自验证 skill |
| Goal-based | 一次手动提示 | 目标达成 OR 轮次上限（评估模型守门） | 停止条件 | **知道"done 长什么样"的任务** | `/goal` |
| Time-based | 时间间隔 | 你取消 / 工作完成 | 触发器 | 例行工作、监视外部系统 | `/loop <间隔>`、`/schedule`（云端） |
| Proactive | 事件/日程，无人在场 | 单任务达标退出；例行直到关闭 | 提示词本身 | 定义清晰的重复工作流 | `/schedule`（research preview）+ `/goal` + dynamic workflows（research preview）+ auto mode |

> `/loop` 跑在本机（关机即停）；要上云用 `/schedule`。（官方 loop.pdf）
> 补充（Claude Code 运行时行为，非 PDF 内容）：`/loop` 不带间隔 = 动态节奏模式，agent 自定下次唤醒时机。

## Standard Workflow

### Step 1: 任务画像（intake）

先问清/探明四件事（用户没给就主动收集动态上下文——读状态表、ls 队列目录、查质量门命令）：

1. **任务形态**：
   - 有限队列（N 个 specs/文件/issue 要全部做完）→ 倾向 Goal-based 长跑
   - 目标收敛（把分数/覆盖率推到阈值）→ Goal-based
   - 监视外部（CI/PR/渠道有变化才动）→ Time-based
   - 常驻流水（持续进来的 bug 报告/反馈）→ Proactive
2. **队列/进度真相源在哪**：哪个文件/表/目录能唯一回答"还剩什么没做"（没有就先让用户建，或在提示词里指定第一步建立）
3. **质量门是什么**：可机械执行的验收命令/评分（tsc、测试命令、build、R_eff 阈值、Lighthouse 分数……）
4. **自主边界**：哪些决策可自决（引用已有决策台账/工作假设），哪些永不自动（部署/对外发布/删数据/花钱）

### Step 2: 原语选型（决策树）

```
工作由外部事件/时间驱动？
├─ 是 → 需要无人值守常驻？ → 是: /schedule (+/goal 组合) ；否: /loop <间隔>
└─ 否（一次触发跑到完）
   └─ done 可确定性验证？
      ├─ 是 → /goal（首选：评估模型替你守停止条件，防"提前宣布完成"）
      └─ 否 → 先把 done 定义成可验证的（回到 Step 3），实在不行才用 turn-based + 自验证 skill
```

超长任务（预计超过单会话上下文）不必回避 /goal——只要队列真相源在磁盘、恢复协议写进提示词，compact/中断后循环仍能续跑。

### Step 3: 停止条件与质量门设计（本 skill 的核心价值）

停止条件三要素，缺一不合格：

| 要素 | 要求 | 反例 → 正例 |
|------|------|------------|
| 完成判据 | 磁盘可验证（文件/状态值/命令输出）+ **字段名对齐磁盘既有模板（先 grep 确认，禁臆造）** | "全部做完" → "28 个 03-tasks.md 收口记录『状态判定』字段（磁盘既有五态字段）已填终态词 ∈ {PASS/…/spec-premise-stale/deferred-non-blocking}" |
| 质量门 | 机械可执行 + 阈值明确 | "保证质量" → "每件 R_eff ≥ 0.95（机械 min 禁手调）+ 每波 tsc/全量测试/build 三绿" |
| 上限阀 | 显式轮次/时间上限 | 无上限 → "stop after 150 turns"（上限命中≠失败，重发同一提示词从磁盘续跑） |

**确定性判据才能让评估模型守门**——loop.pdf 指出：确定性判据（通过测试数、清过某分数阈值）之所以最有效，正因评估模型可以机械判定。

### Step 4: 组装提示词（九块结构 + 契约文件模式）

> **⚠️ 硬限制（2026-07-07 实测）**：`/goal` 条件上限 **4000 字符**。九块全文内联几乎必超限。
> **契约文件模式（/goal 超 4000 字符时的必要形态）**：九块全文写入磁盘「执行契约」文件（放在任务目录旁）；/goal 只装——契约文件绝对路径指针 + 内联精简停止条件（评估模型据此守门）+ 常驻红线摘要 + 上限阀，并写明"开工与每次恢复第一步=完整重读契约"。
> **⚠️ 间接层四条自伤（对抗验证实锤，必须规避）**：(1) 评估模型只读 /goal 不读契约 → /goal 判据里路径必须**全绝对**（相对短名评估器不可解析，守门退化成信 agent 自报）；(2) 违反即不可逆的红线只放契约会被 compact 掉 → 必须**回显进 /goal 常驻**；(3) 判据字段名必须**对齐磁盘既有模板**（臆造字段 → 守门永假 loop 空转）；(4) /goal 里"读契约"等过程祈使要与"完成判据"**句法分区**（否则评估模型可能误当永不满足的完成门）。契约稳健性与内联**相当**（都靠指针存活），不优于内联——能塞进 4000 就内联，省一次重读失败点。生成后必须 `wc -m` 实测 ≤ 4000。

长跑执行类：九块全文进契约文件（模板见 templates/），/goal 走契约指针形态；轻量监视类可全文内联并裁剪到 4-5 块（仍须 ≤ 4000 字符）：

1. **目标与范围清单** — 做什么、多少件、在哪（绝对路径）
2. **队列真相源** — 哪个文件是唯一进度表；"队列 = 磁盘状态，不是对话记忆"
3. **单件循环** — 每件的固定动作序列（如：前提复核 → 实施 → 对抗验证 → 回归门 → commit → 收口记录）。收口记录须含机器可检的**状态字段（沿用目标模板既有字段名，先 grep 确认，禁臆造）**——其终态词集是停止条件判定依据；对抗验证/前提复核结论也写进收口记录，让守门通道能看到（否则可被静默跳过）
4. **质量门** — 阈值 + 命令 + 不达标动作（修复重验，不跳过）
5. **决策政策** — 自主决策依据（决策台账/工作假设）+ 决策留痕位置
6. **中断恢复协议** — 重新进入时先读进度表、先盘磁盘（半成品可能已写完文件）、绝不重做已收口件。长跑要按**五类中断分流**（008 一轮全遇到，见 project-lessons 第 15 条）：周配额硬上限→主线程 solo 降级；并发破坏性 git→待并发方收口后恢复；auth 掉线→先发 ALIVE 探针再 resume；会话/5h 限额→先盘磁盘再补 commit；**TaskList 空 ≠ 工作流死**→凭完成通知判定、勿抢跑（第 17 条）。黄金纪律：撞任何限先盘磁盘再动手
7. **停止条件** — Step 3 三要素
8. **禁止事项** — 不可逆/对外动作 + 项目红线（禁改的标识符/禁跳过的门）+ **运行中的工作流不干预**（宁等勿抢；008 假绿竞速红线，第 17 条）。并发安全：单件循环里每个原子改动落地即 commit，不留长期未提交工作树（缩小被同分支其他 loop 广域 `git add` 扫走的窗口，第 16 条）
9. **终报格式** — 完成后写报告文件（路径固定），含逐件评分表 + 偏差清单 + 遗留项

### Step 5: 输出

交付两样东西：

1. **paste-ready 提示词**（代码块包裹，用户直接复制粘贴；/goal 形式则整条以 `/goal ` 开头）
2. **操作手册**（简短）：
   - 用什么模型跑（长跑执行建议 Opus；判断密集环节用最强模型——loop.pdf: routing routines to smaller models, most capable for judgment calls）
   - 怎么监控：`/goal`（无参数）看轮次与 token；`/workflows` 看子 agent；`/usage` 看用量分布
   - 中断/上限命中后怎么办：重发同一提示词（恢复协议保证从磁盘续跑）
   - 先试跑：第一件跑完人工抽查一次再放手（loop.pdf: pilot before a large run）

## 旗舰场景：大批量 specs 无人值守执行

> 完整参数化模板 + 真实填充示例（009 支付链路 28 套 specs）见 [templates/spec-batch-execution.template.md](templates/spec-batch-execution.template.md)。

要点速记：
- 队列真相源 = requirements/00-INDEX.md 的「实施进度 / 收口表」
- 单件循环 = Step 6.0 前提复核 → 按 03-tasks.md 实施 → 对抗验证 → 波内回归门 → commit → 收口记录写入 03-tasks.md 尾部
- 质量门 = 实施后 FPF 复核 R_eff ≥ 0.95 + 每波 tsc/全量测试/生产 build 三绿（+ 环境预检与 blocked-env 降级分支，禁静默跳过）
- **无收口记录 = 未收口**（完成的唯一证据是写进文件的收口记录，不是对话宣布）；停止条件按收口记录**磁盘既有状态字段**（009 为 ameureka-spec-dev 的「状态判定」五态，先 grep 对齐勿臆造）机械判定，stale/deferred 设数量上限防提前退出后门
- 热点文件串行（多 spec 共改同一文件时禁并行，按热点表错开）
- 防降标与 git 边界条款为骨架内置（禁删测试变绿、禁篡改评分口径、默认禁 push）

## Critical Rules

### ✅ ALWAYS

1. **ALWAYS 把停止条件写成磁盘可验证的确定性判据** — 评估模型才能守门，防提前宣布完成
2. **ALWAYS 设显式上限阀** — "stop after N turns/tries"；上限命中 = 续跑信号，不是失败
3. **ALWAYS 用 `wc -m` 实测 /goal 文本 ≤ 4000 字符** — 超限被运行时直接拒绝（2026-07-07 实锤）；超限走契约文件模式，守好间接层四条自伤：/goal 判据全绝对路径、红线回显进 /goal、字段名对齐磁盘（先 grep）、判据与过程祈使句法分区
4. **ALWAYS 让 /goal 判据自包含且字段名对齐磁盘** — 评估模型只读 /goal 不读契约；判据引用的路径全绝对、状态字段名先 grep 目标模板确认（臆造字段 → 守门永假 → loop 空转到上限）
5. **ALWAYS 把队列真相源放磁盘并写进提示词** — 长跑必然 compact，对话记忆不可依赖
6. **ALWAYS 写中断恢复协议** — 先读进度表、先盘磁盘（死掉的轮次常已写完文件）、绝不重做已完成件
7. **ALWAYS 显式排除不可逆/对外动作** — 部署、发布、删数据、花钱永不进自主范围
8. **ALWAYS 建议先试跑一件再放手** — pilot before a large run

### ❌ NEVER

1. **NEVER 用模糊停止条件**（"做完为止"/"质量足够好"）— 评估模型无法判定，循环会提前退出或永不退出
2. **NEVER 让进度只存在于对话里** — compact 后队列即丢
3. **NEVER 在提示词里省略质量门命令** — "保证质量"没有命令支撑 = 没有质量门
4. **NEVER 生成会并行写同一热点文件的循环** — 共享文件冲突会互相覆盖
5. **NEVER 把"跑到上限"当失败处理** — 恢复协议 + 重发提示词即续跑
