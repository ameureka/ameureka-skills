# 101code 项目长跑实战教训（loop 提示词必须吸收的 19 条）

> 蒸馏来源：009 支付链路专项（8 维审计 Workflow 三段断点续跑 + 28 套 specs 批量生成两轮限额中断全部救回）、006/007 批次收口纪律、004 经营台 Q0-Q5 批量执行、/goal 实战（Stop hook 驱动跑完审计+矩阵+specs 全链）、**008 docs 专项首次端到端跑通（2026-07-08，契约模式 loop 实跑到 12/12 全终态；第 15-19 条为此轮新增，是本 skill 首次「生成的提示词被实际执行到收口」的实证）**。
> 每条都进过收口记录或记忆层，非推测。生成 loop 提示词时逐条对照：适用的必须写进提示词对应块。

## A. 进度与恢复（长跑的生死线）

### 1. 队列真相源必须在磁盘，不在对话记忆
长跑必然触发 compact（上下文压缩）。压缩后 agent 只剩摘要——如果"还剩哪些没做"只存在对话里，队列即丢。
**落法**：提示词指定唯一进度表（如 requirements/00-INDEX.md 的「实施进度 / 收口表」），每完成一件立即更新该表；恢复时以该表为唯一队列依据。

### 2. 无收口记录 = 未收口
"对话里宣布完成"不算完成。完成的唯一证据是**写进文件的收口记录**。给 loop 用时，收口记录必须含机器可检的「最终状态」单值字段 ∈ {PASS, spec-premise-stale, deferred-non-blocking}——修复历程（PARTIAL→已修复、FAIL→已修复等五态词汇）写进证据栏，不混入状态值，否则评估模型对停止条件无法机械裁决（"FAIL→已修复"既不在通过集也不在失败集，循环会烧到上限或诱导改写状态过门）。
**落法**：单件循环的最后一步固定为"写收口记录（固定标题 + 最终状态单值 + 证据）到 03-tasks.md 尾部 + 更新进度表"，两个动作都完成才算该件闭环。

### 3. 中断恢复先盘磁盘再动手
限额中断/网络断线时，死掉的轮次**常常已经把文件写完**、只是没来得及汇报（009 批量生成 specs 两轮中断，10+18 套全部从磁盘救回，零重做）。
**落法**：恢复协议第一条 = 逐件核对磁盘实态（文件是否存在、收口记录是否已写），已完成的直接登记，绝不重做。

### 4. 分块顺序执行 > 一把梭并行（配额韧性）
大批量 fan-out 一次全发，中断时半途状态难收拾；分块（2×9、3×10）顺序执行，已完成块自然落盘，中断只损失当前块。
**落法**：提示词写明批次切分（如"按波次推进，波内逐件串行"）。

### 5. "Connection closed mid-response" 是瞬时网络错误，不是配额
误判成配额会导致不必要的放弃。单发补跑即可。
**落法**：恢复协议注明：瞬时错误→重试当前件；配额/限额→按第 3 条盘点后续跑。

## B. 质量门（防"假完成"）

### 6. 质量门必须机械化，评分禁手调
R_eff = min(D1..D5) 机械计算，禁止手工上调；"质量 95 分" = R_eff ≥ 0.95，不达标先修文档/实现再重评，在本轮内闭环。
**落法**：质量门块写明评分公式 + 阈值 + 不达标动作（修复重验，不跳过、不降标）。

### 7. 每件循环固定六步，顺序不可省
`前提复核(Step 6.0) → 实施 → 对抗验证 → 回归门 → commit → 收口记录`。
- 前提复核：spec 的 file:line 锚点/键名/数量断言对当前 HEAD 重验（specs 写完到执行之间代码会漂移；009 Wave 1 复核发现 4 处漂移，全无害但必须先知道）
- 对抗验证：完成后由**新鲜上下文的第二视角**专门找茬（不是自己夸自己）
- 回归门：tsc + 全量测试 + 生产 build 三绿才 commit（转红即修，不积累欠账）
**落法**：单件循环块逐步列出，标注"顺序固定，禁跳步"。

### 8. 期望值取应然态，禁 pin 观察值
写回归测试时期望值来自"收口后应该是什么样"，不是"现在观察到什么样"——pin 观察值会把 bug 固化成规范。

### 9. runtime > canon：锚点漂移按现状实施并留痕
spec 里的行号/键名与当前代码不一致时，以代码现状为准实施，在收口记录的偏差清单里留一行痕（"等价实施偏差"），不返工 spec 除非语义级冲突（spec-premise-stale 态）。

## C. 并发与冲突

### 10. 热点文件串行，禁并行写
多件共改同一文件（如 stripe.ts 被 5 个 spec 触碰）时并行 agent 会互相覆盖。
**落法**：提示词引用共享文件热点表；同热点的件强制串行（合并者模式），不同热点才可并行。

## D. 决策与边界

### 11. 自主决策要有依据源 + 留痕位置
"遇到决策自己选"不能裸授权——必须指定依据源（决策台账拍板值 / specs 工作假设 / 项目红线）和留痕位置（决策日志文件），选择时与依据源一致的直接执行，超出依据源的记录后选保守项。
**落法**：决策政策块写明：依据序列 = 台账拍板值 > specs 工作假设 > 项目红线下的保守选项；每个自主决策一行记入终报的决策附录。

### 12. 不可逆/对外动作永不进自主范围
部署（生产/灰度）、对外发布、删数据、真实付费操作——即使用户说"全部自动"，也保持人工确认。历史上所有批次的部署都是独立于批量授权的单独确认动作。
**落法**：禁止事项块显式列出；loop 做到"本地 commit 到指定分支为止"——**默认禁 git push**，推送须用户显式授权并写进提示词（操作手册不随 /goal 进 agent 上下文，边界必须写在提示词本体里）。

### 13. /goal 条件上限 4000 字符 → 契约文件模式（2026-07-07 实锤）
009 首跑把九块全文（4811 字符）内联进 /goal，被运行时直接拒绝：`Goal condition is limited to 4000 characters`。
**落法**：超 4000 时双产物——九块全文落盘为「执行契约」文件；/goal 只装契约绝对路径指针 + 内联精简停止条件（与契约【7】语义一致）+ 常驻红线 + 上限阀 + "开工与每次恢复第一步=完整重读契约"。生成后 `wc -m` 实测 ≤ 4000。
**注意**：契约模式稳健性与内联**相当**（都靠 /goal 里的指针存活 + agent 主动重读），**不优于**内联——它多一个"重读被跳过"的失败点。唯一理由是 4000 上限；能内联时优先内联。

### 14. 契约间接层的四条自伤（2026-07-07 二轮对抗验证，1 blocker + 6 major）
把细则从 /goal 外移进契约后，评估模型只看得到 /goal（约 1000 字符），看不到契约——由此产生四个新故障面，生成契约模式提示词时逐条规避：
1. **判据路径必须全绝对**：/goal 判据里的队列表/终报/spec 目录路径若用相对短名，评估器无法解析到磁盘 → 守门退化成信 agent 自报，打穿"评估模型=磁盘可验证"的核心价值。（这是 blocker）
2. **违反即不可逆的红线必须回显进 /goal**：红线只放契约会被 compact 掉；compact 后 agent 手里的常驻 /goal 若不含"禁改标识符/禁 SQL 改余额"，可能真去做。挑 1-4 条最硬的回显进 /goal，完整清单留契约。
3. **判据字段名必须对齐磁盘既有模板**：009 契约臆造「最终状态」字段，而 ameureka-spec-dev 生成的 28 份 spec 收口记录实际字段是「状态判定」（五态），磁盘 0/28 有「最终状态」→ 严格守门找不到字段 → 停止条件永假 → loop 空转到 turn cap。**生成前必须 grep 目标模板确认真实字段名与取值集**，别让磁盘迁就提示词。
4. **判据与过程祈使句法分区**：把"开工先读契约"这类不可磁盘验证的过程祈使塞进 condition 判据句，评估模型可能当成永不满足的完成门（→烧到上限）。用 `[执行前提，非停止判据]` / `[完成判定，只守这四项纯磁盘事实]` 显式分区。
附加：契约文件/终报要在契约里声明"只读、非实施对象"，否则落在被反复 commit 的目录里可能被 agent 好心改坏（恢复锚点污染）；对抗验证/前提复核的结论要写进收口记录，否则它们在守门通道零足迹、可被望文生义 agent 静默跳过。

## E. 008 端到端首跑实证（执行韧性 —— 提示词被真正跑到收口才暴露的层）

> 第 1-14 条来自「生成提示词 + 跑批量 specs 生成」阶段；009 的 loop 未跑到实施收口。008 是本 skill **首次「生成的 /goal 被实际执行到 12/12 全终态」**。执行态才暴露的教训集中在此。

### 15. 五类中断恢复矩阵（008 一轮全遇到，恢复协议必须分类处置）
长跑不是「会不会中断」而是「哪种中断」。008 单轮 loop 命中五种不同中断，各有专属恢复动作——恢复协议块若只写「先盘磁盘再动手」不够，要按类分流：

| 中断类型 | 表现（008 实况） | 专属恢复动作 |
|---|---|---|
| **周配额硬上限** | fan-out 的 subagent 17 秒即被毙、**零落盘** | 主线程 **solo 降级**（自己兼实施者+证伪者，收口记录标注降级）；或等配额重置后重发同一 /goal |
| **并发破坏性 git** | 同分支另一 loop 的广域 `git add`/reset **两次扫走我未提交的 sed 编辑** | 待并发方收口后再恢复；已 commit 的不丢（→见第 16 条预防） |
| **auth 瞬时掉线** | 轮次报 `Not logged in · /login` | 先发 1 个 **ALIVE 探针 agent** 探测恢复，再 resume workflow（勿盲目重发全量） |
| **会话 / 5h 限额** | agent 死于 commit **之前** | **先盘磁盘**（死 agent 常已写完文件只丢返回值）→ 主线程 disk-recovery 补 commit |
| **误判工作流死** | TaskList 空被误读成 agent 死 | **不动**（→见第 17 条）：`TaskList 空 ≠ 工作流死`，确认完成通知再说 |

**黄金纪律（008 实锤救回 3 处）**：**撞任何限先盘磁盘再动手**。008 的 UI-003 Task0 基线、CODE-002 守护测试、UI-008 llms.txt+48 日期全部从磁盘救回，零重做。恢复协议块必须把这条列为第一动作，并附上「瞬时错误（第 5 条 Connection closed）重试当前件 / 配额限额盘点后续跑」的分流。

### 16. edit→即时 commit，缩小并发扫入窗口（并发安全）
008 期间并发的 009 loop 用广域 `git add .` 两次把我**未提交的编辑**一并 commit/丢弃。根因不是对方恶意，是「未提交的工作树改动」对任何同分支 loop 都是暴露面。
**落法**：单件循环里「实施完一个原子改动就立即 commit」，别攒一批再提交——把「可被别的 loop 扫走」的窗口压到最小。提示词的单件循环块可加一句「每个原子改动落地即 commit，不留长期未提交工作树」。这条与第 12 条（默认禁 push）不冲突：commit 到本地分支是缩小暴露面，push 才是对外动作。

### 17. 运行中的工作流绝不干预（假绿竞速，新增红线）
008 我误判 TaskList 空 = CODE-002 的实施 agent 已死，主动提交了一个「恢复」commit（`a7cda290`）去续它的活。但那个 agent **仍在跑**——我的提交与它竞速，恰好捕获了它注入变异测试的中间态，产出**假绿**。
**落法**：① 恢复协议明确 `TaskList 空 ≠ 工作流死`，必须凭**完成通知/终报落盘**判定工作流真结束，才动同一工作树；② 这条要进提示词的**禁止事项块**（新红线：「运行中的工作流不干预，宁等勿抢」）。**幸存教训**：008 的对抗验证是独立 agent，工作流自身的验证 agent 抓获并修复了我的假绿——再次印证「验证者与实施者必须不同实例」（第 7 条对抗验证）的兜底价值。

### 18. 契约文件模式（v1.1/v1.2）跨多次中断续跑，实证成立
008 实跑印证契约模式可用性：**1902 字符 /goal**（含全绝对路径判据 + 回显红线 + 上限阀）+ 九块契约落盘，扛过第 15 条五类中断多次 compact/resume，最终跑到 12/12 全终态，零队列丢失。
**确认要点**：(i) /goal 判据全绝对路径 → 评估模型每次都能真读磁盘守门（非信 agent 自报）；(ii) 硬红线回显进 /goal → compact 后仍常驻；(iii) 每次恢复第一步「完整重读契约」被 agent 稳定执行。→ 第 13-14 条的契约模式设计经受住了真实执行，可放心用于旗舰长跑。

### 19. 停止条件按磁盘既有字段机械判定 + deferred≤N 上限，实证防提前退出
008 停止条件用 ameureka-spec-dev 收口记录的**磁盘既有五态字段（先 grep 对齐、非臆造，正是第 14.3 条要求）**机械判定 12 件全终态：10 件 PASS 类 + 2 件 `deferred-non-blocking`。两个 deferred（DEP-001 需 workflow-scope push、UI-006 tool-loop 需真 key）都是**环境不允许**的诚实降级，各自写明触发器。
**落法**：② 停止条件把 `stale + deferred` 合计设**显式上限（008 用 ≤4；实际 2/12）**——上限的作用是堵「把做不动的件全标 deferred 提前退出」的后门，评估模型见 deferred 超限即判未收口、不放行。这条把第 6/第 2 条的「无收口记录=未收口」在停止判据层做成可机械裁决的闭环。

## 附：/goal 实战观察（本项目）

- /goal 在本项目实际用于"跑完审计 → 生成需求矩阵 → 生成 specs 全链"，Stop hook 会在每次试图停止时检查目标——**目标文案里的交付物定义越具体（路径级），守门越准**。
- /goal 的常设授权同时激活了两个 skill 的"批量授权模式"（映射确认降级为事后审查）——生成提示词时如果下游 skill 有确认门，要在提示词里显式声明授权模式，否则循环会卡在确认门上等人。
- 上限命中/会话中断后，重发同一 /goal 提示词 + 恢复协议 = 无损续跑（磁盘真相源保证幂等）。
