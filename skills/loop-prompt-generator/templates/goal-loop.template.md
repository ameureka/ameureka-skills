# 模板：通用 /goal 目标收敛 loop

> 适用：把某个可测量指标推到阈值（测试通过数/覆盖率/性能分/错误清零），或一次性有限任务跑到 done。
> 与旗舰模板的区别：目标单一、通常不需要队列真相源与波次编排，五块即可。

---

## 提示词骨架（五块）

```
/goal {{一句话目标，含确定性判据与阈值}}，stop after {{N}} {{tries|turns}}。

【验证方式】
done 的判定命令/方法：{{可机械执行的命令 + 期望输出}}。每轮结束用它自验，不达标继续。

【工作方式】
{{关键约束：改哪里/不改哪里；用什么测试；转红即修}}

【禁止事项】
{{红线：不可逆动作/禁改文件/禁降标（如禁删测试来"让测试变绿"）}}

【完成动作】
达标后：{{commit 要求 / 输出摘要格式}}。
```

## 要点

- 目标句必须含**数值阈值或布尔判据**（"90 分以上""0 errors""全部通过"），评估模型才能守门。
- 上限阀语法直接放在 /goal 首行（官方示例：`/goal get the homepage Lighthouse score to 90 or above, stop after 5 tries.`）。
- **防降标条款必写**：优化指标类任务要显式禁止"作弊路径"（删测试、放宽断言、跳过用例、篡改评分脚本）。
- 若任务其实是有限队列（多件全部做完），改用旗舰模板 spec-batch-execution。

## 填充示例

```
/goal 把 token101-v2.1 的 pnpm test 单测失败清零（当前 3 个红），stop after 10 tries。

【验证方式】
cd /Users/ameureka/Desktop/101code/token101-v2.1 && pnpm test —— 退出码 0 且输出含 "failed" 的行数为 0。

【工作方式】
只修实现或测试中确证错误的一方；先读失败输出定位根因再动手；每修一个跑相关文件级测试，全清后跑全量确认。

【禁止事项】
禁止删除/skip 测试用例来变绿；禁止放宽断言精度；禁止改动与失败无关的文件；禁止任何部署/推送动作。

【完成动作】
全绿后 commit（fix: ...，Conventional Commits），回复逐个失败的根因一行摘要。
```
