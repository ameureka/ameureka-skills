# DRR (Design Rationale Record)

## 什么是 DRR

DRR（Design Rationale Record）是**设计理由记录**，用于记录：
- 做了什么决策
- 为什么这样决策
- 考虑了哪些替代方案
- 决策的后果是什么

DRR 是 FPF 流程的最终产出，确保决策可追溯、可审计。

---

## DRR 格式规范

```markdown
# DRR-{序号}-{标题}

**Created**: {时间戳}
**Status**: Active | Superseded | Deprecated

## Context (背景)

描述问题和约束条件。

- 我们面临什么问题？
- 有哪些约束条件？
- 为什么需要做这个决策？

## Decision (决策)

我们决定使用 {方案}。

简洁明了地陈述决策内容。

## Rationale (理由)

### R_eff 对比

| 假设 | R_eff | 最弱环节 |
|------|-------|----------|
| {获胜方案} | {分数} | {WLNK} |
| {被拒方案1} | {分数} | {WLNK} |
| {被拒方案2} | {分数} | {WLNK} |

### 关键优势

- 优势 1
- 优势 2
- 优势 3

### 风险评估

- 风险 1 及缓解措施
- 风险 2 及缓解措施

## Consequences (后果)

### 需要做什么

- [ ] 行动项 1
- [ ] 行动项 2
- [ ] 行动项 3

### 预期收益

- 收益 1
- 收益 2

### 潜在风险

- 风险 1
- 风险 2

## Validity (有效期)

何时需要重新评估此决策：

- 条件 1 发生时
- 条件 2 发生时
- 或在 {日期} 之后

## Relations (关系)

- **selects**: {获胜假设ID}
- **rejects**: [{被拒假设ID1}, {被拒假设ID2}]
- **supersedes**: {被替代的DRR ID}（如果有）
```

## Transformer Mandate

### 核心原则

> **系统不能自我转换。**

这意味着：
- Claude 生成选项和证据
- **人类做最终决策**
- Claude 记录决策理由

### 为什么重要

1. **责任归属**：决策责任在人类，不在 AI
2. **可审计性**：决策过程透明可追溯
3. **避免偏见**：防止 AI 的隐性偏见影响决策

### 违规示例

```
❌ 违规：自主决策

"Redis 的 R_eff 是 0.85，比 CDN 的 0.72 高，
所以我决定使用 Redis，现在开始实现..."

问题：
- AI 自己做了决策
- 没有等待用户确认
- 没有调用 quint_decide
```

```
❌ 违规：引导性决策

"Redis 明显是更好的选择，您同意吗？"

问题：
- 使用引导性语言
- 暗示了"正确答案"
- 没有中立呈现选项
```

### 正确流程

```
✅ 正确：中立呈现 + 等待选择

[调用 quint_calculate_r 获取各假设 R_eff]

"以下是各方案的对比：

| 方案 | R_eff | 最弱环节 | 主要优势 |
|------|-------|----------|----------|
| Redis | 0.85 | 内部测试 | 低延迟 |
| CDN | 0.72 | 外部文档 | 全球分发 |

请问您选择哪个方案？"

[等待用户回复]

用户: "我选择 Redis"

[调用 quint_decide 记录决策]
```

## DRR 生命周期

### 状态定义

| 状态 | 含义 |
|------|------|
| Active | 当前有效的决策 |
| Superseded | 被新决策替代 |
| Deprecated | 已废弃，不再适用 |

### 状态转换

```
Active ──────────────────────────────▶ Deprecated
   │                                      ▲
   │                                      │
   └──▶ Superseded ──────────────────────┘
           │
           │ (新 DRR 创建)
           ▼
        Active (新)
```

### 替代决策

当需要修改之前的决策时：

1. 创建新的 DRR
2. 在新 DRR 中添加 `supersedes: DRR-XXXX`
3. 将旧 DRR 状态改为 `Superseded`

## 关系图

DRR 创建后会建立以下关系：

```
                    ┌─────────────┐
                    │    DRR      │
                    │ DRR-0001    │
                    └──────┬──────┘
                           │
           ┌───────────────┼───────────────┐
           │               │               │
           ▼               ▼               ▼
    ┌─────────────┐ ┌─────────────┐ ┌─────────────┐
    │   selects   │ │   rejects   │ │   rejects   │
    │ redis-cache │ │  cdn-edge   │ │  lru-cache  │
    └─────────────┘ └─────────────┘ └─────────────┘
```

### 关系类型

| 关系 | 方向 | 含义 |
|------|------|------|
| selects | DRR → 假设 | 选中的方案 |
| rejects | DRR → 假设 | 被拒绝的方案 |
| supersedes | 新DRR → 旧DRR | 替代关系 |

## 最佳实践

### 1. Context 要具体

```
❌ 模糊：
"我们需要缓存"

✅ 具体：
"用户列表 API 响应时间 > 500ms，数据库查询是瓶颈。
约束：预算有限，团队熟悉 Redis，需要支持分布式部署。"
```

### 2. Decision 要简洁

```
❌ 冗长：
"经过仔细考虑各种因素，我们最终决定..."

✅ 简洁：
"我们决定使用 Redis 作为缓存层。"
```

### 3. Rationale 要有数据

```
❌ 主观：
"Redis 感觉更好"

✅ 客观：
"Redis R_eff: 0.85，CDN R_eff: 0.72。
Redis 的内部测试显示延迟降低 80%。"
```

### 4. Consequences 要可执行

```
❌ 模糊：
"需要配置 Redis"

✅ 可执行：
"- [ ] 部署 Redis 集群（3 节点）
 - [ ] 配置连接池（最大 100 连接）
 - [ ] 添加缓存失效逻辑
 - [ ] 设置监控告警"
```

### 5. Validity 要明确

```
❌ 模糊：
"以后再看"

✅ 明确：
"当以下情况发生时重新评估：
 - 日活用户超过 100 万
 - Redis 成本超过 $500/月
 - 或在 2025-06-01 之后"
```

## 完整示例

```markdown
# DRR-0001-use-redis-for-caching

**Created**: 2024-12-26T10:30:00Z
**Status**: Active

## Context (背景)

用户列表 API 响应时间超过 500ms，影响用户体验。
分析显示数据库查询是主要瓶颈，相同查询重复执行率 > 70%。

约束条件：
- 预算：$200/月以内
- 团队：熟悉 Redis，不熟悉 Memcached
- 部署：需要支持 3 个区域的分布式部署

## Decision (决策)

我们决定使用 Redis 作为 API 响应缓存层。

## Rationale (理由)

### R_eff 对比

| 假设 | R_eff | 最弱环节 |
|------|-------|----------|
| Redis 缓存 | 0.85 | 内部基准测试 |
| CDN 边缘缓存 | 0.72 | 外部文档 (CL1) |
| 应用内 LRU | 0.65 | 分布式一致性问题 |

### 关键优势

- 团队已有 Redis 经验，学习成本低
- 支持分布式部署，满足多区域需求
- 内部测试显示延迟降低 85%（500ms → 75ms）

### 风险评估

- **缓存一致性**：使用 TTL + 主动失效双重策略
- **Redis 故障**：配置 Sentinel 实现高可用

## Consequences (后果)

### 需要做什么

- [ ] 部署 Redis Sentinel 集群（3 节点）
- [ ] 实现缓存层抽象接口
- [ ] 添加缓存命中率监控
- [ ] 配置告警（命中率 < 80% 时）
- [ ] 编写缓存失效逻辑

### 预期收益

- API 响应时间降低 80%+
- 数据库负载降低 60%+
- 用户体验显著提升

### 潜在风险

- 缓存穿透：需要实现空值缓存
- 缓存雪崩：需要随机化 TTL

## Validity (有效期)

当以下情况发生时重新评估：
- 日活用户超过 50 万
- Redis 成本超过 $300/月
- 出现缓存一致性严重问题
- 或在 2025-06-01 之后

## Relations (关系)

- **selects**: redis-caching
- **rejects**: [cdn-edge-cache, in-memory-lru]
```
