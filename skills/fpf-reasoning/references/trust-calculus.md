# 信任计算 (Trust Calculus)

## 核心概念

### R_eff (Effective Reliability)

R_eff 是假设的**有效可靠性分数**，范围 0-1。

- **0**: 完全不可靠
- **0.5**: 中等可靠
- **1**: 完全可靠

R_eff 不是估计值，必须通过 `quint_calculate_r` 工具计算。

---

## WLNK 原则 (Weakest Link)

### 核心公式

```
R_eff = min(所有证据分数)
```

**关键点**：取最小值，不是平均值！

### 为什么用最小值？

一个系统的可靠性取决于最弱的环节。就像一条链子，强度由最弱的一环决定。

### 示例

假设有 3 个证据：
- 内部测试: 0.95
- 代码审查: 0.90
- 外部文档: 0.60

```
❌ 错误计算（平均值）：
   R_eff = (0.95 + 0.90 + 0.60) / 3 = 0.817

✅ 正确计算（WLNK）：
   R_eff = min(0.95, 0.90, 0.60) = 0.60
```

外部文档的低分数拉低了整体可靠性。

## Congruence Level (CL) 惩罚

### CL 定义

| CL | 含义 | 惩罚 | 示例 |
|----|------|------|------|
| CL3 | 同一上下文 | 0% | 在本项目中运行的测试 |
| CL2 | 相似上下文 | 10% | 类似技术栈的案例研究 |
| CL1 | 不同上下文 | 30% | 通用博客文章、不同语言的示例 |

### 惩罚计算

```
调整后分数 = 原始分数 × (1 - 惩罚率)
```

### 示例

外部文档原始分数 0.85，来自不同上下文 (CL1)：

```
调整后分数 = 0.85 × (1 - 0.30) = 0.85 × 0.70 = 0.595
```

### CL 判断指南

| 证据来源 | 典型 CL |
|----------|---------|
| 本项目单元测试 | CL3 |
| 本项目集成测试 | CL3 |
| 本项目基准测试 | CL3 |
| 同技术栈开源项目 | CL2 |
| 官方文档示例 | CL2 |
| 技术博客（同语言） | CL2 |
| 通用最佳实践文章 | CL1 |
| 不同语言的实现 | CL1 |
| Stack Overflow 答案 | CL1-2 |

## 依赖传播

### 规则

如果假设 A 依赖假设 B：

```
A.R_eff ≤ B.R_eff
```

依赖的 R_eff 会向上传播，限制父假设的最大可靠性。

### 示例

```
API Gateway (A)
├── Auth Module (B): R_eff = 0.80
└── Rate Limiter (C): R_eff = 0.90

A 的最大 R_eff = min(B.R_eff, C.R_eff) = min(0.80, 0.90) = 0.80
```

即使 A 自身的证据分数是 0.95，由于依赖 B，A.R_eff 最高只能是 0.80。

### 依赖 CL 惩罚

依赖关系也有 CL 惩罚：

```
依赖贡献 = 依赖.R_eff × (1 - CL惩罚)
```

示例：
- Auth Module R_eff = 0.80
- 依赖 CL = 2 (10% 惩罚)
- 依赖贡献 = 0.80 × 0.90 = 0.72

## 审计树可视化

### 格式说明

```
hypothesis-a [R:0.72]
├── evidence-1 [R:0.85]
├── evidence-2 [R:0.72] ◄── WLNK (最弱环节)
└── dependency-b [R:0.80] (CL:2)
    └── evidence-3 [R:0.90]
```

### 符号说明

| 符号 | 含义 |
|------|------|
| `[R:X.XX]` | R_eff 分数 |
| `(CL:N)` | Congruence Level |
| `◄── WLNK` | 最弱环节标记 |
| `├──` | 子节点 |
| `└──` | 最后一个子节点 |

## R_eff 解读指南

| R_eff 范围 | 解读 | 建议行动 |
|------------|------|----------|
| 0.90 - 1.00 | 高度可靠 | 可以放心采用 |
| 0.75 - 0.89 | 较为可靠 | 可以采用，注意监控 |
| 0.60 - 0.74 | 中等可靠 | 谨慎采用，加强验证 |
| 0.40 - 0.59 | 可靠性存疑 | 需要更多证据 |
| 0.00 - 0.39 | 不可靠 | 不建议采用 |

## 提高 R_eff 的方法

### 1. 加强最弱环节

找到 WLNK，针对性加强：

```
当前：
- 内部测试: 0.95
- 外部文档: 0.60 ◄── WLNK

改进：
- 添加更多内部测试验证外部文档的说法
- 或找到更权威的文档来源
```

### 2. 提高 CL

将低 CL 证据替换为高 CL 证据：

```
❌ CL1: 通用博客文章
✅ CL3: 在本项目中运行验证脚本
```

### 3. 减少依赖

如果依赖拉低了 R_eff，考虑：
- 独立实现（消除依赖）
- 加强依赖项的验证

## 偏见检查 (D.5)

在计算 R_eff 时，还需检查认知偏见：

### Pet Idea 偏见

**症状**：对某个方案有不合理的偏好

**检查**：
- 是否给"喜欢"的方案更宽松的评分？
- 是否忽略了该方案的弱点？

### Not Invented Here 偏见

**症状**：排斥外部方案

**检查**：
- 是否公平评估了第三方解决方案？
- 是否因为"不是自己写的"而低估？

### 确认偏见

**症状**：只寻找支持预设结论的证据

**检查**：
- 是否主动寻找反面证据？
- 是否考虑了方案的失败场景？

## 实际计算示例

### 场景

评估 "使用 Redis 缓存" 假设

### 证据收集

| 证据 | 类型 | 原始分数 | CL | 调整后分数 |
|------|------|----------|-----|------------|
| 本地基准测试 | internal | 0.90 | CL3 | 0.90 |
| Redis 官方文档 | external | 0.85 | CL2 | 0.765 |
| 技术博客案例 | external | 0.75 | CL1 | 0.525 |

### R_eff 计算

```
R_eff = min(0.90, 0.765, 0.525) = 0.525
```

### 分析

- WLNK: 技术博客案例 (0.525)
- 建议: 用内部测试替代博客案例，或找更权威的来源

### 改进后

| 证据 | 类型 | 原始分数 | CL | 调整后分数 |
|------|------|----------|-----|------------|
| 本地基准测试 | internal | 0.90 | CL3 | 0.90 |
| Redis 官方文档 | external | 0.85 | CL2 | 0.765 |
| 生产环境验证 | internal | 0.88 | CL3 | 0.88 |

```
R_eff = min(0.90, 0.765, 0.88) = 0.765
```

R_eff 从 0.525 提升到 0.765。
